# 寻道MUD 游戏内容设计模式

> 本文件记录在 XunDaoMUD 项目中已验证的游戏内容设计流程和模式。
> 可用于后续同类内容（矿石、渔获、怪物掉落、装备、技能等）的快速设计。

---

## 通用工作流

```
Emma 出设计稿（名称+备注+风格说明+数值草案或交互流程）
    ↓ 呈交给用户审核
用户反馈调整
    ↓ 如有修改
Emma 更新设计稿
    ↓ 用户审核通过（"完美"/"拍板"/"让小弟开工吧"）
路由小弟按设计稿实现代码（code-task skill）
```

### 文件拆分 — Hub 保持向后兼容

当将一个大文件拆分为 N 个分类文件时，不要直接删除原文件并修改所有消费者。而是**保留原文件为纯 re-export hub**：

```python
# 原文件（已空，仅作为合并中心）
from world.money_templates import ITEM_TEMPLATES as _MONEY
from world.equipment_templates import ITEM_TEMPLATES as _EQUIP
# ... 其他分类 ...
ITEM_TEMPLATES = {}
for _d in (_MONEY, _EQUIP, ...):
    ITEM_TEMPLATES.update(_d)
```

**好处：**
- 所有消费者的 import 不需要改一行
- 新分类文件可以独立维护、独立注册
- 未来新增分类只需在 hub 加一行 import + update
- 不需要做全项目 grep 改 import

**使用场景（2026-07-24 item_templates.py 拆分为 5 个分类文件）：**
- consumer 文件（game_util.py / at_server_startstop.py / quest.py）零改动
- 新增 money_templates.py / equipment_templates.py / skill_book_templates.py / material_templates.py / talisman_templates.py
- item_templates.py 从 167 行缩为 15 行 hub
```

## 案例：52种药材系统（2026-07-11）

### 1. 命名风格梯度

| 品级 | 风格 | 例子 |
|:----|:-----|:-----|
| 一品 | 朴实直白，像路边野草 | 青灵草、止血草、石生花 |
| 二品 | 带点灵气，稍有辨识度 | 聚灵草、月华草、朝阳花 |
| 三品 | 有修仙感，"紫/玄/玉"字辈 | 紫阳灵芝、玄霜草、碧玉藤 |
| 四品 | 珍稀感，"炎/冰/九/血"等 | 炎阳花、冰魄莲、血菩提 |
| 五品 | 千年/龙/凤等传说前缀 | 千年雪莲子、龙涎仙草、凤凰灵花 |
| 六品 | 先天/混沌/造化级 | 混沌青莲、太乙玄参、鸿蒙紫参 |

### 2. 环境分布维度

每种药材标注生长环境，为后续地图房间分布做准备：

| 环境 | 低→高成长链 |
|:----|:-----------|
| 🔥炎热 | 赤精叶(二) → 炎阳花(四) → 赤焰芝(四) → 凤凰灵花(五) |
| ❄️寒冷 | 寒露草(二) → 玄霜草(三) → 冰魄莲(四) → 千年雪莲子(五) |
| 🌿灵气 | 聚灵草(二) → 紫阳灵芝(三) → 九叶灵芝(四) → 九转还魂草(六) |
| 🌑阴气 | 凝露花(一) → 银芽芝(二) → 血菩提(四) |
| 🪨特殊地貌 | 石生花(一) → 地脉参(二) → 碧玉藤(三)/龙骨草(三) → 地母藤(四) |
| 🌌传说秘境 | 雾隐芝(三) → 七星草(四) → 龙涎仙草(五) → 混沌青莲(六) |

### 3. 稀有度池数学

按熟练度分级的概率分布，新等级从 **1%** 起步，按 **1% → 3% → 10% → 25%** 递增：

```
CAI_YAO_RARITY_POOLS = [
    {"min_pro": 0,         "pool": [95,  5,  0,  0,  0,  0]},   # 纯新手
    {"min_pro": 10,        "pool": [92,  8,  0,  0,  0,  0]},   #
    {"min_pro": 100,       "pool": [88, 12,  0,  0,  0,  0]},   #
    {"min_pro": 1000,      "pool": [84, 15,  1,  0,  0,  0]},   # 🆕三品 1%
    {"min_pro": 10000,     "pool": [80, 16,  3,  1,  0,  0]},   # 🆕四品 1%
    {"min_pro": 100000,    "pool": [68, 18, 10,  3,  1,  0]},   # 🆕五品 1%
    {"min_pro": 1000000,   "pool": [40, 21, 25, 10,  3,  1]},   # 🆕六品 1%
    {"min_pro": 10000000,  "pool": [17, 20, 25, 25, 10,  3]},   # 六品 3%
]
```

**开放节奏：** 三品 @1k、四品 @10k、五品 @100k、六品 @1M
**核心原则：** 控制顶级产出以保护经济循环，顶级药材永远稀有

### 4. 物品模板落地格式

```python
HERB_NAME: dict = {
    "key": "中文名",
    "template_key": "qing_ling_cao",        # 小写下划线英文
    "item_type": ItemType.MATERIAL,          # 药材用 MATERIAL
    "rarity": Rarity.TIER_1,                # 1-6 对应品级
    "value": 5,                              # 按稀有度递增
    "stackable": True,
    "unit": "株",
    "desc": "最常见的灵草，遍布皆是，蕴含微弱的灵气。",
}
# 文件末尾自动注册到 ITEM_TEMPLATES
```

### 5. 房间采集池模式（Room Pool Only — No Global Fallback）

每个可采集的房间拥有自己的采集池（`db.cai_yao_herbs: list[str]`），存放本房间可产出的药材 template_key。

- **房间池为空时的行为：** 空池 = 没货。不产出任何物品，玩家只收到"没有发现"的提示。**无 global fallback。**
- **筛选逻辑：** roll 出稀有度后，从房间池筛选该品级的药材 → 随机选一个。如果该品级在池中无匹配，走降级/失败逻辑。
- **优势：** 每个房间的产出可独立控制（如火山地带不出寒凉药材），方便做地图生态
- **模板化：** Room 类初始化时设 `self.db.cai_yao_herbs = []`，后续在 room_templates.py 中按 room 逐个配置

```
采集流程：
roll 稀有度（1-6品）
  → 房间池有配置且该品级有货？ → 随机选一个
     ↓ 否
  无产出（"没有发现可采的药材"）
```

> ⚠️ **历史教训（2026-07-11 采药回退bug）：** 采药最初错误地在房间池为空时回退到全量 `HERB_TEMPLATES`，导致"农田"以外不该出药材的房间也出药材。已修复。**新建**生活技能（如挖矿）的产出逻辑时，不要引入类似的 global fallback。

## 案例：52种矿石系统（2026-07-11）— 跨品类命名

### 1. 命名风格梯度

矿石与药材是**完全不同的物品品类**，命名要体现金属/玉石/晶体质感，避免与药材的字面和意境重复：

| 品级 | 风格 | 例子 |
|:----|:-----|:-----|
| 一品 | 基础灵材、精炼金属 | 精铜、精铁、银砂、碎灵石 |
| 二品 | 灵性矿材、玉石晶体 | 玄铜、暖玉、墨晶、碧玉 |
| 三品 | 稀有矿物、高阶金属 | 玄铁、秘银、金刚玉、赤焰晶 |
| 四品 | 珍稀灵矿、天外来物 | 炎阳玉、玄冰晶、陨铁精、五色玉 |
| 五品 | 传说级神矿 | 星辰金、九天玄铁、雷劫玉 |
| 六品 | 宇宙本原级 | 太初玄金、混元金、无极天晶、亘古玄铁 |

### 2. 跨品类命名碰撞规避

这是**本 session 验证的核心教训**。当在同一个游戏里创建第二个物品品类时，必须主动检查与第一个品类的命名冲突：

| 检查维度 | 药材（已存在） | 矿石（新设计） | 处理方式 |
|:---------|:--------------|:--------------|:---------|
| **六品用词** | 混沌、造化、鸿蒙、太乙、九转、阴阳 | 太初、混元、无极、亘古、太极、九霄 | **零共用词**，换个意境的词 |
| **三~四品** | 紫阳/玄霜/碧玉/龙骨/玉髓 | 炎阳玉/玄冰晶/紫晶砂/金刚玉 | 矿石用"玉/晶/砂"后缀 vs 药材"草/花/藤/芝"后缀，自然区分 |
| **植物类词** | 草/花/藤/芝/莲/参 | **完全不用** | 矿石用金属/玉石/晶体词根 |
| **生态词** | 气候、地貌、植物特征 | 矿物特性、物理质感 | 描述角度不同（药材：生长环境；矿石：材质特性） |

**操作方法：**
1. 设计初稿时，列出两个品类中**可能重叠的关键词**（六品的"鸿蒙""混沌""造化"在药材中已使用，矿石就不能再用）
2. 如果某个品级的意境方向已被占据（如六品药材走"混沌造化"风），矿石就走不同的意境方向（"宇宙本原"风：太初、混元、亘古）
3. 优先保证 **最高品级（五/六品）的命名完全不重复**——这是玩家记忆最深、辨识度最高的内容
4. 三~四品靠**后缀/品类词**自然区分（药材是"草/花/藤/芝"，矿石是"玉/晶/砂/金"）

### 3. 设计迭代过程示例

```
V1（失败）：石灰石、砂岩、黏土、煤块 — ❌ 对修仙者无用
             鸿蒙石、混沌晶、造化玉  — ❌ 与药材六品用词重复

V2（失败）：砍掉建材类，金属/玉石/晶体方向 ✓
             但六品依然叫"鸿蒙石""混沌晶" — ❌ 用词与药材重复

V3（通过）：六品换太初/混元/无极/亘古/太极/九霄 ✓
             一品用精铜/精铁/银砂/碎灵石 ✓
             三~四品用"玉/晶/砂/金"后缀 vs 药材的"草/花/藤" ✓
```

### NPC 对话内容设计模式

#### 命名风格偏好：接地气，不文绉绉

游戏角色名（NPC、村民等）应该亲切朴实，像真实的人名而非小说角色：
- ✅ **好例子：** 张有福、刘大壮、李老根、王大锤
- ❌ **坏例子：** 张守正、林骁、田耕、铁熔

命名时优先考虑：村里怎么喊这个人？而不是"这个名字有没有文化底蕴"。
修仙世界观的表现力靠物品名、功法名、地点描述来撑，角色名反而要**下沉**才真实。

### 引导型 NPC 设计原则

- **宁少勿多：** 功能指引 NPC 默认只给 **1 个核心分支**就够了。一段话能讲完的信息量别拆成三个分支。
- **严格按需求：** 用户说了"两个对话话题"就精确写两个，不额外加戏。不要创作用户没要求的内容分支。
- **人设嵌入内容：** 用 NPC 的口吻自然透露信息（老农说"那些杂草"而非"一品灵草"），比额外加一段"背景故事"更高效。

### NPC 模板结构（参考 world/npc_templates.py）

```python
NPC_NAME: dict = {
    "key": "laonong",              # 英文标识，用于 ask <key>
    "npc_name": "老农",             # 显示名称
    "room_key": "清泉镇东",         # 生成房间（无此字段则默认清泉镇）
    "desc": "人物外观描述...",
    "default_response": "无匹配关键词时的默认回应",
    "dialogues": {
        "关键词": {
            "response": "对话内容...",
            "show_if": {},           # 条件显示（quest_flag/not_flag/quest_state）
            "actions": [],           # 对话后动作（set_flag/accept_quest/remove_items）
        },
    },
}
```

### 常见坑

- **scope creep：** 用户说"采药指引+农田介绍"就写这两个分支，不额外加"杂草详解""背景故事"等分支
- **对话长度：** 每个分支 3-5 句话为宜，超过 8 句就需要大幅精简
- **|C命令名|n 上色：** Evennia 中用 `|C` 标记给命令名高亮，帮助玩家识别可交互元素

## 交互功能设计模式

### 子命令面板模式（用于交互式 UI 命令）

当需要一个**多步/多选交互界面**（如出售面板）时，采用子命令模式：

```
sell                  — 打开面板，显示当前状态
sell <编号>           — 切换单个选项
sell <编号> <数量>     — 指定数量
sell all              — 全选
sell clear            — 清空选择
sell confirm          — 确认执行
sell cancel           — 取消
```

**设计原则：**
- **不进入特殊模式** — 玩家不需要"进入"和"退出"出售模式，每个子命令是独立的，随时可输入其他指令
- **状态存 ndb** — session 级别的购物车用 `caller.ndb` 存储，断线自动清空
- **每次操作刷新面板** — 子命令执行后重新格式化面板文本输出，给玩家即时反馈
- **confirm 时重新校验** — 确认时重新计算价格和检查背包状态，防止 confirm 之前物品已被其他操作消耗

**适用的场景：** 出售、批量合成、批量丢弃、战利品拾取确认、邮件附件管理等

### 3 系统并行扩展模式

当游戏引入一个新的**内容维度**（如物品品级 rarity）时，需要同步扩展三个系统：

| 系统 | 位置 | 扩展内容 | 用途 |
|:----|:-----|:---------|:-----|
| **Trigger 系统** | `_check_single_trigger` | `item_rarity:TIER_X` | 任务 completion_trigger 检查 |
| **Condition 系统** | `_check_conditions` | `item_rarity:TIER_X` | NPC 对话 show_if 条件检查 |
| **Action 系统** | `_execute_actions` | `remove_items` 支持 `item_rarity` | 对话后按品级移除物品 |

**流程验证（2026-07-24 iron ore quest）：**
1. 先扩展 Trigger → `completion_triggers: ["item_rarity:TIER_1"]`
2. 再扩展 Condition → 对话交付分支的 `conditions: {"item_rarity": "TIER_1"}`
3. 最后扩展 Action → `{"type": "remove_items", "item_rarity": "TIER_1", "quantity": 1}`

> **教训：** 设计新任务/对话流程时，提前想清楚这个链路的三个环节是否都支持新维度。忽略任何一个环节都会导致交付对话卡住（condition 不满足 / action 无法移除物品）。

### 交互设计阶段的审核要点

在给哥哥提交交互功能设计稿时，主动暴露以下 edge cases：

| 问题 | 卖出面板例子 |
|:----|:------------|
| 总量不足时怎么办？ | 选中物品总价 < 1 灵石时阻止出售，提示"没什么价值" |
| 堆叠物品怎么处理？ | 支持 `sell <编号> <数量>` 指定部分，默认全量 |
| 状态跨 session 吗？ | 用 ndb 存储购物车，断线自动清空 |
| 环境依赖？ | 检查当前房间是否有带 shop 的 NPC，没有则提示 |
| 操作中途环境变化？ | confirm 时重新校验背包和 NPC 状态 |

在首次设计稿中主动问清楚这些边界情况，比被 user 指出来再改更高效。

## 通用坑清单

### 数量确认
用户说"1-2品12种"时要确认是**各12种**（总计24）还是**总共12种**（一品6+二品6）。
> 教训（2026-07-11）：Emma 以为"一品12+二品12=总计24"但实际上用户说的是各12，理解正确但需要确认。

### 数值方案验证

当设计涉及**资源/修为消耗阈值、概率分布、伤害数值等**的游戏机制时，必须先验算实际游戏公式，再提交给用户审核。

**验证流程：**

1. **找到相关曲线函数** — grep 项目中的公式（`curve_cultivation`、`curve_max_resource`、`curve_attack_strength` 等）
2. **计算真实累计值** — 用 Python 跑出各境界/等级的累计修炼量、平均每级成本等
3. **将设计阈值与曲线对比** — 算出入门占比（threshold / total_to_reach_tier × 100%）
4. **估算玩家感受** — 结合修炼速度公式估算攒够该阈值所需时长（分钟）
5. **呈现对比数据给用户** — 老阈值 vs 新阈值 vs 曲线数值，让用户一眼看出合理性

**典型案例（2026-07-22 推演修为阈值 — 5 轮迭代）：**

```
初始设计：练气=0, 筑基=100, 金丹=500  ← 💀 未验算，随口填的
实际曲线：到筑基一层累计 107,811 修为，100 点仅占 0.09%
Round 2：按大境界总修炼量比例缩放到 ~10%  ← ❌ 漏算"突破要扣钱"
             → 突破到金丹要花掉累计修为的大半，刚突破玩家掏不出阈值
Round 3：按突破后余额反算比例  ← ❌ 练气巅峰掏不出筑基价
             → 练气巅峰才 ~10K 修为，设 5K 门槛太高（伪灵根坐牢 42 分钟）
Round 4：练气巅峰存量门控 + 伪灵根最差路径精算  ← ✅ 通过
             → 练气=500, 筑基=10K(≥巅峰存量), 金丹=80K(≥筑基巅峰)
最终：每档 = 上一大境界巅峰存量（即"不突破就够不着下一档"）
      伪灵根从零到第一次推演 ≈ 18 分钟（练气二层）
      真灵根从零到第一次推演 ≈ 3 分钟
```

**不验算的后果：** 低境界玩家轻松推演出本不该获得的高境界词条（投入 500 修为就解锁金丹池，而金丹需要 80 万累计修为），经济循环崩溃。

> **规则：** 所有数值设计稿在提交用户审核前，必须至少跑一次算数验证。不作为的"大概合理"会被打回来。

### 奖励变更的 consequential audit
当修改**任务奖励**（quest_data.py 的 rewards）或**NPC 对话**时，必须 grep 项目确认没有遗漏引用旧内容：

```
# 改完任务奖励后，检查 NPC 对话是否还在提旧奖励
grep -r "铁剑\|布甲" world/npc_templates.py
# 结果：镇长"兔毛"分支还在说"这把铁剑和这件布甲你先用着" → 需要同步更新
```

**影响面清单：**
- 任务奖励变更 → 检查 giver/turn_in NPC 的对话文本
- 物品改名/删除 → 检查 NPC 对话、任务描述、帮助文本
- NPC 职责变更 → 检查其他 NPC 的对话（是否还在指引玩家到旧 NPC 处）

> 教训（2026-07-24）：从镇长任务移除铁剑/布甲后，镇长的交付对话仍写着"这里有三样东西给你——这把铁剑和这件布甲你先用着"，造成内容不一致。

### 顶级物品开放节奏
- 新稀有度从 **1%** 起步，按 **1% → 3% → 10% → 25%** 递增开放
- 过早开放高级物品（熟练度<1k就出三品以上）会破坏经济循环

### 命名区分度
- 一品和六品的名字不能混淆 — 一品起"混沌XX"会让玩家产生预期错位
- 不同品级间的名称要有递进感（一品朴实 → 四品珍稀 → 六品传说）

### use() 消耗物品必须更新背包 slot
当物品的 `use()` 方法销毁/消耗自身时，必须同步更新 `caller.db.inventory` 列表，不能只改 `self.db.quantity`：

```python
# ❌ 错误：只改对象属性，不碰背包列表
self.db.quantity -= 1
if self.db.quantity <= 0:
    self.delete()

# ✅ 正确：先清理背包 slot，再删除对象
for idx, slot in enumerate(caller.db.inventory or []):
    if slot and slot["dbref"] == self.id:
        caller.remove_from_inventory(idx, slot["quantity"])
        break
self.delete()
```

背包系统存储两份数据：
- `caller.db.inventory` 列表 — 每个 slot 存 `{"dbref": id, "quantity": N}`
- `item.db.quantity` — 物品对象的自身数量属性

**只改 `item.db.quantity` 不碰 `caller.db.inventory` 的后果：**
- `_used_slots()` 仍将 slot 计为已占用 → 格子数不减
- `_find_empty_slot()` 跳过该 slot → 新物品从后续编号开始
- `show_bag()` 查不到已删除对象 → 物品不显示但格子占着

> 教训（2026-07-24 skill_book_item.py:39）：`SkillBookItem.use()` 只做了 `self.db.quantity -= 1` 和 `self.delete()`，导致使用引气术后背包 slot 被幽灵占用。修复方案是在 `self.delete()` 前遍历 inventory 找到对应 slot 并调用 `caller.remove_from_inventory()`。

### 环境链完整度
每个环境方向要有从低到高的完整成长链条：
```
例：炎热环境：赤精叶(二) → 炎阳花(四) → 赤焰芝(四) → 凤凰灵花(五)
                  ↑                          ↑              ↑
              低级可采                   中级可采       高级可采
```
不能出现某个环境只有低级或只有高级物品的情况。

### 跨品类命名碰撞检查清单

设计新品类前，**必须** grep 现有品类的高品级关键词，确保零共用词：

```python
# 自检流程（以矿石 vs 药材为例）：
# 1. 列出已有品类各品级的关键词
#    药：一品"草/花/藤/芝"，六品"混沌/造化/鸿蒙/太乙/九转/阴阳"

#    矿：一品"铜/铁/砂/石"，六品"太初/混元/无极/亘古/太极/九霄"
# 3. 三~四品靠后缀自然区分

## 案例：技能词条设计模式（2026-07-22 推演系统 + 2026-07-24 灵技词条）

### 1. `rarity=0` 标记约定

词条库中 `rarity` 字段承担双重职责：

| 值域 | 含义 | 示例 |
|:----|:-----|:-----|
| `rarity = 0` | 🚫 **不进入玩家推演池** — 怪物专属、基础攻击、NPC 行为等 | `base_attack(r=0)`, `beast_pounce(r=0)`, `蛇毒(r=0)` |
| `rarity ≥ 1` | ✅ **玩家可推演抽取** | `聚气壹(r=100)`, `伤害·金(r=100)`, `穿透(r=90)` |

**设计原则：** `rarity = 0` 是在推演系统（`_draw_affix_candidates`）中统一过滤的语义标记。凡是设计为"只给怪物用/只做底层引用/不给玩家直接获取"的词条，就设 `rarity=0`。

**验证方法：** 新增词条时，如果它不应该出现在 `ty` 推演菜单的候选列表中，`rarity` 就填 0。

> 教训（2026-07-22）：推演系统首次上线后玩家抽到了「猛兽扑咬」「普通攻击」「蛇毒」等怪物专属词条。修复方案是在 `_draw_affix_candidates` 中追加 `rarity > 0` 过滤，并将此约定设为标准。

### 2. 词条品质分档逻辑（quality tiering）

推演系统用词条自身的 `rarity` 字段做品质分档（不是技能品阶 rarity，是词条 detail 的 rarity 字段）：

| 品质档 | rarity 范围 | 显示标签 |
|:-------|:------------|:---------|
| 普通 | ≤ 30 | `[普通]` |
| 精良 | 31–60 | `[精良]` |
| 稀有 | > 60 | `[稀有]` |

**抽取流程：** 先按品质权重抽档次（受投入资源价值影响）→ 从档内按词条 rarity 加权抽具体词条。

### 3. 3选1候选词条模式

```python
_draw_affix_candidates(skill_type, rarity, char, exclude_keys, quality_value)
  → 最多 3 条 dict，按品质权重 + 排除已选 key 过滤
```

- `exclude_keys` 保证已选词条不重复出现
- 池子不足 3 条时有多少返多少
- 品质权重受 `resource_value × 4^(rarity-1)` 影响
- 玩家手动选一条，保留自由度而非全自动

### 4. 多维词条命名约定

当词条名字包含**多个维度**（如技能类型 + 元素 + 品阶）时，用 `·` 分隔各维度，形成清晰的三段式结构：

```python
# 格式：[大类]·[子类]·[品阶]
# 示例：
"伤害·金·壹"    # 灵技 → 金属性 → 壹阶
"伤害·火·叁"    # 灵技 → 火属性 → 叁阶
# 注：单维度词条（如"聚气壹""迅捷壹""疾行壹"）不需要加分隔符
#     只有包含 ≥2 个分类维度的词条才用此模式
```

**命名规则：**
- `·` 分隔的每一段代表一个独立的分类维度
- 品阶编号（壹贰叁肆伍陆）在最后一维
- 单维度系列（聚气壹~陆、迅捷壹~陆、疾行壹~陆）保持原样，不加多余分隔符

### 5. 基础伤害词条设计原则

**基础五行灵技**（伤害·X）是最烂大街的词条，设计时应遵循以下原则：

| 原则 | 说明 |
|:----|:-----|
| **低门槛** | 灵根要求统一 15（有对应灵根就能推，不设门槛意义） |
| **长线战斗** | 纯基础伤害击杀同阶敌人需 **7-12 次**，境界越高越难 |
| **后期鼓励 combo** | 后期增伤手段丰富，基础伤害故意压低，逼玩家叠 buff/打 combo |
| **数值估算流程** | 先拉 `curve_max_resource(level, gen_gu)` 算 HP → 再定 base_damage |

**估算流程（Python）：**

```python
RESOURCE_BASE = {1: 10, 2: 100, 3: 1000, 4: 10000, 5: 100000, 6: 1000000}
SUB_REALM_RATE = [1.0, 1.15, 1.30, 1.50, 1.75, 2.00, 2.30, 2.65, 3.00, 4.00]
REALM_BASE = [0.1, 0.35, 1.50, 7.00, 30.0, 150.0, 900.0]

def max_hp(level, gen_gu=100):
    if level == 0:
        return 10 + gen_gu // 10
    tier = (level - 1) // 10 + 1
    index = (level + 9) % 10
    return int(RESOURCE_BASE[tier] * (1.225**index) * (gen_gu / 100) + 25)

def calc_damage(base_damage, level, attack=150, defense=150):
    rp = SUB_REALM_RATE[(level-1)%10] * REALM_BASE[min((level+9)//10, 6)]
    atk_rate = 1.0 if attack <= 100 else (attack / 100.0) ** 0.45
    raw = int(base_damage * rp * atk_rate)
    final = int(raw * (1 - defense / (defense + 500)))
    return final

# 检查：base_damage=N 时击杀同阶刚入门的敌人需要多少下
hp = max_hp(11)     # 筑基入门 HP≈125
dmg = calc_damage(12, 11)  # 2阶灵技筑基入门伤害
hits = hp / dmg     # 应落在 7-12 之间
```

> **教训（2026-07-24）：**  Emma 最初设计的 2-6 阶五行灵技目标是 3 次击杀，被用户指正——\"后期增伤手段丰富，基础伤害太高大家都是一刀死\"。改为 7-12 次击杀，境界越高越难纯靠基础伤害打死敌人，鼓励 combo 玩法。
