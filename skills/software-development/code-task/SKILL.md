# code-task — 通用路由 Skill（无例外版）

> ⚠️ **核心原则：所有代码任务强制走 OpenCode。** 本 skill 的唯一职责是"把用户的需求清晰、无歧义地传达给 OpenCode"。你不分析问题根因、不出设计方案、不提供自己的结论——这些会污染小弟的独立判断。**没有例外。**

## 什么时候用

用户让你做以下事情，且需要走 OpenCode 小弟执行时，路由到本 skill：

### 🧑‍💻 代码修改类
- 写功能、修 Bug
- 重构、调优
- 写测试

### 🔍 分析类
- **问题定位** — "为什么 X 不工作"、"这个 bug 的根因是什么"
- **模块设计** — "帮我设计 X 模块"、"这个功能应该怎么实现"
- **项目重构** — "分析一下项目结构的优劣"
- **技术债分析** — "扫一下代码中的技术债"
- **架构审查** — "检查项目架构是否合理"

> 无论是改代码还是分析，本 skill 走同一路由流程：**消歧 → 判断任务类型/选模型 → 写 prompt → 执行**。区别在 prompt 结构和模型选择。

### 不做的事
- ❌ 不分析根因（Emma 不分析，交给小弟）
- ❌ 不出设计方案（Emma 不出，交给小弟）
- ❌ 不提供自己的分析结论给小弟
- ❌ 不代替用户做模糊决策（除非用户明确说"你来定"）

> ⚡ **例外 — 用户主动征求设计意见：** 当用户明确问"你觉得这个设计怎么样？"/"你有什么建议？"时，可以给出**简短的设计反馈**再路由给小弟。这不算 Emma 擅自分析，而是回应直接提问。原则：只指出明显的设计问题和方向建议（2-3句话），不做深度分析；反馈后立即切入消歧/路由流程。

### ✅ Emma 的 PM 分析职责（区别于送小弟的技术分析）

当用户说"帮我看看现有代码有什么、还缺什么才能实现这个设计"时——**这不属于"送小弟的技术分析"，而是 Emma 作为 PM 的正规分析职责。**

核心区别：

| 类型 | 谁做 | 产出 | 典型用户话术 |
|:----|:-----|:-----|:------------|
| **🔬 技术分析** | → 小弟（pro 模型） | 设计方案、根因结论、架构评估 | "帮我设计 X"、"为什么 X 不工作"、"分析架构" |
| **📋 PM 差距分析** | → Emma | 现有设施清单、缺失模块表、改动量级预估 | "帮我看现有代码还缺什么"、"分析需要开发哪些模块" |

**判断准则：**
- 你的产出是"先搞清楚设计意图 + 对齐现有代码，再让小弟去做" → **Emma 做的 ✓**
- 你的产出是"这是设计文档/根因结论/实现方案" → **该送小弟 ✗**

**PM 差距分析的标准流程（本 session 演示的模板）：**
1. **理解设计** — 复述用户的设计意图，确保理解正确
2. **代码库深度侦察** — grep 搜索所有与设计相关的现有设施（属性、命令、常量、效果、房间标记、模板等），边搜边读关键文件
3. **分类差距** — 按 ✅ 已存在 / ⚠️ 有骨架但需补全 / ❌ 需要新建 三级标记
4. **输出差距分析报告** — 按依赖顺序列出每个模块的改动量级、文件路径、建议策略
5. **路由实现** — 分析完成确认后，按本 skill 标准流程 dispatch 给小弟

> **⚠️ 注意：** PM 分析的输出只是"差距清单"（哪些已存在，哪些需要新建），不包含具体实现方案。具体的模块设计、代码实现仍然交给小弟。差距分析报告可以写进小弟 prompt 的【背景事实】段作为上下文，但不能包含 Emma 的设计判断（"这里应该用 X 模式"之类）。

代号「哥哥」的用户对以下习惯性表达**明确反感**：

| ❌ 不要 | ✅ 要 |
|:--------|:------|

## Phase 0：消歧

在你做任何操作之前，先判断用户的需求是否足够明确。

### 需要消除的歧义维度

| 维度 | 需要问的问题 | 通过标准 |
|:----|:------------|:--------|
| **做什么** | "你是要修代码还是做分析？"（当类型不明确时） | 明确是改代码还是分析 |
| **改/分析什么** | "具体要改哪一个/些文件？" / "具体要分析哪个模块？" | 精确文件路径或明确的搜索条件 |
| **改成什么样 / 分析到什么程度** | "预期的行为变化是什么？" / "分析到架构级还是实现级？" | 具体描述，不是"修好它"这种 |
| **不改什么 / 不分析什么** | "有没有哪些文件/模块是不能动的？" | 明确的边界约束 |
| **为什么** | "这个改动的背景/目的是什么？"（仅当意图不明确时） | 理解上下文才能写对 prompt |
| **交付要求** | "需要出修复方案还是直接改代码？需要跑测试吗？" | 明确的完成标准 |

### 消歧原则

1. **持续追问** — 一个维度没消除就继续问，不做猜测
2. **不替用户做决定** — 除非听到"你来定"、"你自己决定"、"你看着办"
3. **把歧义摆在台面上** — "你说的'优化'具体指性能优化还是代码结构优化？这两者的改动方向完全不同。"
4. **对模糊用词直接质疑** — "重构"、"优化"、"修好"、"整理"、"调整"这些词必须先问清楚具体含义
5. **先判断任务类型** — 用户说了一通之后，先确认是代码修改还是分析任务，因为后续流程不同

### UI/UX 设计消歧（当用户提出面板/组件/图形界面设计时）

当用户描述一个**可视化组件、游戏面板、前端 UI 或交互卡片**的设计时，上述代码消歧维度不足以覆盖 UI 特有的歧义。追加以下维度：

| 维度 | 要问的问题（按优先级） | 通过标准 |
|:----|:---------------------|:--------|
| **🎨 视觉样式** | "颜色规则是什么？渐变还是定值？有状态阈值吗？" | 明确每个元素的颜色、大小、高/宽、阈值条件 |
| **🖱 交互行为** | "可点击吗？点击发什么命令？hover/scroll 行为？" | 明确每个可交互元素的触发方式和效果 |
| **📡 数据驱动** | "什么时候刷新？每 tick 还是事件驱动？数据来源是什么？" | 明确更新时机、消息格式、发送方 |
| **⚡ 边界情况** | "XX 没有这个属性怎么办？数据为空时显示什么？" | 明确缺失/空值/极限状态的渲染策略 |
| **🔮 预留设计** | "这个区域标注了预留/未来，现在怎么处理？" | 明确留空还是占位，确保不阻塞当前实现 |

> **2026-06-21 战斗面板设计（验证案例）：** 本 session 用这 5 个维度问了 6 个问题，全部一次对齐。
> - 视觉：三资源条颜色 + 百分比阈值（HP>60%绿/20-60%橙/<20%红，MP蓝，SP紫）
> - 交互：buff/debuff tag 可点击 → 发命令到游戏面板
> - 数据：事件驱动（加扣血、获得/失去 buff 时刷新），非 tick 轮询
> - 边界：怪物无 MP/SP → 卡片不显示该行
> - 预留：永久效果栏留空，未来补

### 消歧完成的标准

- ✅ 明确知道任务是改代码还是做分析
- ✅ 明确知道涉及的路径或模块范围
- ✅ 明确知道要改成什么行为 / 分析到什么深度
- ✅ 明确知道边界约束（不改/不碰什么）
- ✅ 明确知道完成标准（出方案还是直接改？验不验测试？）
- ✅ 所有模糊用词已被具体描述替换
- ✅ (UI 设计) 上述 5 个 UI 维度已确认

## Phase 1：判断任务类型与模型选择

任务明确后，先判断是**分析类**还是**代码修改类**，再选模型。

### 任务类型判断

用户说的话里出现以下信号时归类：

| 信号词 | 类型 |
|:------|:----|
| "分析"、"定位"、"根因"、"为什么"、"排查"、"调查"、"检查"、"审查"、"扫描"、"评估"、"审计" | 🔍 **分析类** |
| "做"、"写"、"实现"、"改"、"修"、"删"、"加"、"重构"（明确要改代码） | 🧑‍💻 **代码修改类** |
| "设计"（模块/功能/系统） | 先消歧是出设计文档 → 走 plan skill；如果是让小弟设计 → 🔍 分析类 |

#### ⚡ 组合型任务："分析并修复"

当用户说"分析一下是什么原因"、 "看看为什么" 等分析性表述，但**上下文暗示需要一并修复**（如不修好了用户不会再回来问），这就是 **组合型任务**（分析 + 代码修改）。

处理规则：
- **模型** → 一律 **`deepseek-v4-pro`**（根因不明 == 复杂任务）
- **Prompt 结构** → 用代码修改 prompt 模板，但在"任务"段开头加上"先分析根因，再实现修复"
- **【背景事实】段** → 只放源码事实（文件路径、函数签名、数据流路径），不放 Emma 的分析推测
- **交付要求** → 分析结论 + 代码改动 + 验证结果都要
- **默认不要分两阶段**（先分析再单独派修）— 用户一次说完的事，一次派给小弟，让小弟自己分析完直接修

> **例外 — 用户明确分阶段：** 当用户明确说「你先分析原因/分析一下什么情况，再派小弟修」时，**遵循用户的分阶段指令**。先 Emma 读代码定位根因 → 告知用户分析结论 → 等用户确认后再 dispatch。dispatch prompt 中只放源码事实，不夹带 Emma 的分析结论（用户已经看到了，小弟需要独立验证）。
>
> 判断标准：用户是否明确把"分析"和"修"分成两条指令说。如果写在一个句子里（"分析然后修一下"）→ 默认走组合型一次派完。如果分两句或两轮说（"先分析原因"→等回复→"让小弟修"）→ 分阶段处理。

判断标准：用户的话里包含分析类的信号词（"分析"/"看看"/"为什么"），但最终想要的产出是改好的代码（不是分析报告）。此时归为组合型，用 Pro 模型一次解决。

### 🔍 分析类任务

| 属性 | 值 |
|:----|:---|
| **模型** | **一律 `deepseek-v4-pro`**（分析需要深度推理能力） |
| **OpenCode skill** | 按任务类型加载对应 skill（见下） |
| **背景** | **只给事实**（错误日志、现象、文件路径、已尝试但无效的方案），**不给 Emma 的分析结论** |
| **输出** | 分析结论含证据 + 建议方案（不改代码只出建议）。不承诺一定会去实现 |

### 🧑‍💻 代码修改类任务

#### 🔴 复杂任务 → deepseek-v4-pro

满足**任意一条**就归为复杂：

| 特征 | 例子 |
|:----|:-----|
| **架构级重构** | 拆分模块、重新分层、消除循环依赖、Mixin 化大 class |
| **新模块/新文件设计** | 新建一个完整的系统（如功德系统、战斗引擎、消息队列） |
| **跨 3+ 文件的联动改动** | 新增功能需要改 typeclasses + commands + cmdsets |
| **框架/底层行为调试** | 需要理解 Evennia CmdSet 合并机制、ORM 查询优化等 |
| **安全/协议/系统集成** | 实现 OAuth、MCP 协议、外部 API 集成 |
| **根因不明的 Bug** | 不能一眼定位到具体行号，需要多文件追踪数据流 |
| **需要理解业务逻辑的改动** | 修仙境界突破逻辑、功德结算规则等有领域复杂度的改动 |
| **大文件（>300行）的核心逻辑修改** | 战斗引擎、技能系统等核心逻辑文件的修改 |

#### 🟢 简单任务 → deepseek-v4-flash

**全部满足**才归为简单：

| 特征 | 例子 |
|:----|:-----|
| **单文件改动** | 只改一个文件 |
| **改动范围小（<30行）** | 修一个 typo、改一个变量名、加一个 if 判断 |
| **一眼能看出根因** | 变量名写错、import 漏了、缩进不对 |
| **纯配置/数据变更** | 改 YAML/JSON/TOML，改常量值，加注释 |
| **测试编写（对已有代码）** | 为已有函数写测试，不改生产代码 |
| **格式化/lint 修复** | ruff 自动修复、删除无用 import |
| **文案/日志/注释修改** | 改 log 信息、修文档字符串 |

#### 默认规则

拿不准时，**默认用 Pro**。宁可多花点 token，也不要因为模型能力不够导致小弟做无用功。

> **历史教训（2026-06-14）：** Emma 默认全用 Flash，结果 CLI 测试挂了 8 个。用户指出的核心问题就是"惯性默认 Flash，没主动评估复杂度"。每次派活前停一秒想清楚。

## Phase 2：写 High-Signal Prompt

### 🧑‍💻 代码修改 prompt 结构

```markdown
## 任务
[一句话描述要做什么]

## 项目路径
[绝对路径]

## 改什么
- 文件 1: [精确路径] — 改什么（具体行为变化）
- 文件 2: [精确路径] — 改什么

## 不改什么
- [不动的文件/功能/模块清单]

## 约束
- [技术约束：如 TDD、Conventional Commits、PII 检查]
- [流程约束：如需要先跑 xxx 命令看一下当前状态]
- [产出约束：如不需要写测试]
- **提交要求：所有改动完成后必须 git commit + git push 到 dev 分支。commit 消息使用 Conventional Commits 格式。**

## 验证
- [如何确认改动有效：跑什么命令、看什么结果]

## 交付要求
1. 改了哪些文件、具体改了什么
2. 验证结果（语法检查、功能验证）
3. 确认改动的文件中没有个人身份信息（PII）
4. git commit hash + push 确认（来自 `git log -1`）
```

### 🔍 分析类 prompt 结构

```markdown
## 分析任务
[一句话描述分析目标]

## 项目路径
[绝对路径]

## 背景事实
- [只放事实：错误日志、现象、文件路径、已尝试但无效的方案]
- [不包含 Emma 的任何分析结论或推测]

## 分析范围
- [具体要分析哪些文件/模块]
- [分析到什么粒度：问题定位级、架构级、技术债级]

## 参考资源
- CLAUDE.md 在项目根目录
- docs/ 目录有设计文档
- 可用 OpenCode skills（通过 skill({ name: "..." }) 加载）：
  - `architecture-analysis` — 架构/技术债分析
  - `debugging-workflow` — 根因调试
  - `code-review-workflow` — 质量门禁 + 审查响应
  - `branch-completion-workflow` — 分支收尾
  - `git-worktree-setup` — 工作区隔离
- 如果当前任务适合 SDD，可加载 sdd-workflow

## 交付要求
1. 分析结论（含证据：日志、源码引用、测试结果）
2. 如果有多个根因可能，列出优先级
3. 建议的修复方案（不改代码只出建议）
4. 确认输出中不含 PII
```

### 可选 Prompt 增强（加在 prompt 末尾）

以下增强可根据任务性质选择性添加：

**自我审查要求（适用于所有代码修改任务）：**
> **自我审查：** 实现完成后，请你自己审查一遍自己的改动。检查：逻辑正确性、边界情况、命名一致性、是否有调试代码残留。确认无误后再提交。

**技术债意识（适用于修改/重构任务）：**
> **顺手还债：** 如果在你改动的文件附近发现可以顺手清理的小问题（过时注释、未使用导入、命名不一致等），一并修复。如果发现结构性技术债，记到 TECH_DEBT.md 中。

**知识库意识（适用于任何任务）：**
> **增量 DOM 更新要求（适用于周期性刷新 UI 的任务）：**
> **增量 DOM 更新：** 所有周期性刷新的 UI 组件，必须使用增量更新模式。首次渲染创建 DOM 结构，后续更新只修改已有元素的属性（`width`、`text`、`class` 等），禁止清空后重建。

**给地图，不给说明书：** AGENTS.md 是项目目录索引，遇到不熟悉的模块时，先去 docs/ 或对应的源码目录探索，不要直接假设实现方式。

**独立分析要求（适用于问题定位/根因分析任务）：**
> **独立分析：** 不要依赖任何已有的分析结论。请从零开始阅读源码、追踪数据流。如果发现和已有分析不同的结论，直接汇报。

### 写 Prompt 的铁律

1. **不夹带 Emma 的分析结论** — "我认为根因是 X"、"我建议用 Y 方案"这类话一句都不能有。如果用户提供了分析，也只作为"用户认为"的背景信息附上，不标注"Emma 认为"
2. **引用用户原话** — 如果用户自己说了想怎么改，直接引用
3. **给地图不给说明书** — 告诉小弟 CLAUDE.md/docs/ 在哪，不把整个文档内容贴进去
4. **明确的边界** — "不改什么"和"改什么"同等重要
5. **通过标准可验证** — 不要"修好它"，要"跑 `pytest xxx -v` 返回 PASS"
6. **交付必须是已提交的代码** — prompt 中必须要求小弟 git commit + push。如果小弟只改了代码没提交（常见），Emma 必须接手走 code-project skill 做 add → commit → push → 告知用户。
7. **系统级改动先做 Reciprocal Sweep** — 移除/重命名/重构某个功能时，不要只盯着眼前文件。先 grep 全项目找所有关联引用，分类后把要改的写进 prompt。详见上面的[系统级改动的 Reciprocal Sweep](#系统级改动的-reciprocal-sweep防漏改) 章节。

8. **Prompt 写需求不写代码（不准抄代码进 prompt）** — 在 prompt 中描述"要什么行为"（改什么、行为变化是什么、做成什么样），**不贴 Python 代码**。告诉小弟"参考 cultivate.py 的模式在 stop 命令追加 caiyao 分支"就够了，**不需要**把 stop.py 或 cultivate.py 的代码复制粘贴进 prompt。小弟的任务是根据需求描述 + 参考现有模式去写代码，不是照着 Emma 给的代码翻译。

   | ✅ 正确（只说行为，不提实现细节） | ❌ 错误（包含了代码片段） |
   |:----------------------------------|:--------------------------|
   | "在 stop 命令中追加 elif 分支处理 idle_task == 'caiyao' 的停止，参考 cultivate 和 liaoshang 的分支写法。" | "```python\nelif caller.ndb.idle_task == 'caiyao':\n    _stop_caiyao(caller)\n    caller.msg('你停止了采药。')\n```" |

   例外：
   - **纯数据/纯内容配置**（药材模板、JSON、YAML、常量列表）的格式和字段名可以精确描述，因为这是数据结构约定而非逻辑实现
   - **内容/行为里程碑规格**（如进度消息文案、操作反馈文本、交互提示）可以精确描述，因为这是需求规格而非实现逻辑
   - **接口锅炉板代码**（如遵循已有精确模式的 3-5 行回调/委托方法，接口签名继承）可以使用模板片段展示，因为这是接口契约匹配而非逻辑实现

   > **历史教训（2026-07-11 采药 prompt）：** Emma 在采药系统 prompt 中贴了代码片段（stop 分支的 elif 实现、at_caiyao_tick 回调的实现），被用户指出"你不要直接把代码传给小弟，你负责准确转述开发需求"。从那以后改为只描述行为+参考模式，不再复制代码。
   >
   > **历史教训（2026-07-22 研读 prompt）：** 此 session 在研读系统的 prompt 中包含了 `at_study_tick` 的三行回调代码。这是有风险的——虽然回调只委托给 `_study_tick(self)` 且是 player_character.py 中第 4 个完全相同的回调模式，但严格来讲仍是 Python 代码。**安全边界：** 如果小弟能通过看文件中其他 3 个同类回调（at_xiulian_tick/at_liaoshang_tick/at_caiyao_tick/at_wakuang_tick）推断出写法，就不该写进 prompt。只有在新文件中创建首个此类回调、且没有任何参考模式时，才应展示模板。

### 内容类 Prompt 的陷阱（NPC 对话、文案、描述等）

当任务包含游戏内容（NPC 对话、物品描述、房间文本、任务剧情、命名、数值）时，先判断属于哪种内容：

| 内容类型 | 处理方式 | 例子 |
|:--------|:---------|:-----|
| **已有明确需求**（用户说了具体写什么） | 直接写进 prompt 让小弟实现 | "NPC 要说这三句话..." |
| **需要命名的内容池**（物品名、技能名等） | **Emma 先设计** → 用户审核 → 再派小弟 | 药材命名、怪物命名、装备命名 |
| **数值平衡**（概率分布、价格、属性值） | **Emma 先出草案** → 用户审核 → 再派小弟 | 稀有度池、掉落率、修炼速度 |
| **需要创作的文案**（房间描述、物品描述） | 写出风格约束+示例 → 让小弟按模板批量生成 | 52种药材的描述文本 |

> **进阶技巧：数据驱动数值迭代** — 当设计涉及**游戏经济、修炼曲线、消耗品定价、概率分布**等数值时，不要凭空提案。先提取代码中的实际公式（`curve_cultivation`、突破阈值、修炼速度等），写 Python 脚本计算多路径场景（最差/最优/平均玩家），再基于数据提案。详见 `game-balance-design` 技能。
>
> **历史教训（2026-06-22 推演门槛设计）：** Emma 连续 4 轮提案都被用户否定——因为每轮都漏算了一个玩家路径（累计修炼量≠可支配余额、突破后余额、伪灵根坐牢时间）。只有从代码提取实际曲线 + 多路径精算后，提案才通过。每次被否定都是因为数据不完整，不是方向不对。

**命名/数值类内容的正确流程（本 session 验证）：**

```
Emma 出设计稿（命名+备注+风格说明）
    ↓ 呈交给用户审核
用户反馈调整（命名风格、数量分布、数值梯度）
    ↓ 如有修改
Emma 更新设计稿
    ↓ 用户审核通过
路由小弟按设计稿实现代码
```

**命名设计原则：**
- 不同稀有度/等级的名字要有明显区分度（一品朴实、六品传说感）
- 名字本身暗示稀有度（别给一品起"混沌青莲"，也别给六品起"轻灵草"）
- 考虑生态多样性（不同环境对应不同物品，为后续内容填充留空间）
- 每个名字附带简短备注，说明其风格和用途
- **风格偏好 接地气**：名字要像真人真物，避免文绉绉/典故堆砌。NPC 名用"张有福、刘大壮、李老根、王大锤"这类亲切朴实的，不要"张守正、林骁、田耕、铁熔"这类偏文学的。修仙味靠物品和世界观呈现就够了，角色名可以土但要有真实感。

> **历史教训（2026-07-11 采药命名）：** 用户要求 52 种药材，一品12 + 二品12 + 三品8 + 四品8 + 五品6 + 六品6。Emma 最初误解为总计 26 种（一品6 + 二品6 等），好在用户指正后补充。设计时要仔细核对数量要求，特别是当用户说"1-2品12种"时，确认是指总共12种还是各12种。
1. **提供精确内容，不交小弟创作**

**内容风格约束** — 在 prompt 中指明格式约束（如命令名用 `|Cxxx|n` 上色）、长度（"2-3 句话"）、语气（"NPC 说话要有修仙味"）等，减少风格对齐成本。格式不一致比内容错误更难修。

2. **NPC 对话宁少勿多** — 引导型 NPC 的对话分支要克制。除非用户明确要求多个话题，否则默认只给 **1 个核心指引分支**就够了：

   - **功能指引 NPC**（如教采药的老农）→ 一个"采药"关键词就够了（指引命令 + 产物轻提一句），不需要额外做"产物详解""背景故事"等分支
   - **判断标准：** 一段话能讲完的信息量就别切成三个分支。分支一多用户觉得"啰嗦"就要返工。

   > **教训（2026-07-11 老农NPC）：** Emma 设计了三个对话分支（采药指引、农田产物介绍、杂草详解），每个都有大量具体内容。用户反馈"太啰嗦了，改成一个就行"。

### 系统级改动的 Reciprocal Sweep（防漏改）

当一个改动涉及**移除/重命名/重构某个功能**或**修改公式曲线**，影响面横跨多个文件/数据时，不能只盯着眼前改的文件。**只改核心逻辑却不扫关联代码/数据**，是用户 review 时发现漏改的第一大原因。

#### 变体 A：移除/重命名/重构功能的代码扫描

适用于删除功能、重命名 API、重构模块时，需要扫全项目找引用。——即下方标准流程。

在 prompt 写完&派小弟之前，追加一个 **Reciprocal Sweep** 步骤：

```
1. 确定核心改动：比如"移除 equip 的心法装备功能"
2. 确定受影响的关键词集合：如 "equip.*force"、"equip.*心法"、"装备为主心法"、"active_main_force"  
   选择原则：既包括被你改掉的 API（equip force），也包括用户可见的文本（NPC 对话、错误提示、帮助文档）
3. 用 grep 搜索整个项目，收集所有命中位置（排除 .pyc/__pycache__/venv）
4. 按以下分类整理命中结果：
   ┌──────────────┬──────────────────────────────────┐
   │ 已由本次改动覆盖 │ 核心逻辑已改，不需再处理            │
   │ 需要顺带修    │ 废弃引用/错误提示/注释——加进 prompt │
   │ 故意保留      │ 如帮助菜单的 │Cequip│n（物品装备） │
   └──────────────┴──────────────────────────────────┘
5. 把"需要顺带修"的条目写进 prompt 的【改什么】段或作为附注
```

为什么要做这个而不是交给小弟去做：

| 让小弟做 | Emma 做 |
|:---------|:--------|
| 小弟专注核心改动，没余力做全项目扫描 | 你 grep 一下全项目就几十秒的事 |
| 语义判断（"这个 equip 是物品装备还是心法装备"）小弟不一定准 | 你作为项目 PM，边界判断更清晰 |
| 增加 token 消耗和迭代轮次 | 一次到位，减少 follow-up 回合 |

完成标准：grep 关键词后，每个结果要么在本次 commit 中被改了，要么被你判断为"故意保留"且能在交付报告中列出。**零"遗漏"条目。**

> **历史教训（2026-06-20）：** 移除 equip force 功能后，cultivate.py 错误提示里还写着"再用 equip <心法名> force 装备为主心法"。用户 review 时一抓一个准。如果当时做了 reciprocal sweep——grep "equip.*force" → 发现 cultivate.py → 顺手改了→ 一次交付就过关。

#### 变体 B：公式/曲线修改的数据值扫描

当改动涉及**修改游戏平衡公式、数学曲线、伤害计算管线**等时，**数据值比代码引用更容易被遗漏**。公式改了，但所有按旧公式调出来的数值（怪物属性、技能伤害、掉落价值等）全部失效，且 grep 搜不出来（因为数据是数值不是标识符）。

**典型案例（本 session 2026-06-24）：**
- 将 `curve_attack_strength` 从 `attack≤100→1.0` 改为 `(attack/100)^0.5`
- 所有怪物模板的 `attack: 1` 从倍率 1.0 骤降至 0.1（10 倍降幅）
- 结果：猛兽扑咬伤害降为 0（因 defense 削减后 int() 归零）
- grep 完全搜不到——数据值是 `1` 不是函数名

**标准流程：**

```text
1. 确定公式改动：如 curve_attack_strength 从分段改为连续幂曲线
2. 确定受影响的数据来源：
   ┌──────────────────┬──────────────────────────────────────┐
   │ 数据来源          │ 示例                                  │
   ├──────────────────┼──────────────────────────────────────┤
   │ 物品/装备/怪物模板 │ monster_templates.py 的 attack 字段  │
   │ 技能/词条配置     │ affix_templates.py 的 base_damage    │
   │ NPC 对话/任务奖励 │ quest_data.py 的 reward_value         │
   │ 常量默认值        │ game_constant.py 的默认 ATTRIBUTE    │
   │ 文档/注释         │ PLAYER_ATTR_REFERENCE.md 的示例计算  │
   └──────────────────┴──────────────────────────────────────┘
3. 对每个数据来源提问：
   - 这个值/公式假设了旧曲线的什么行为？
   - 新曲线下这个值是否仍然合理？
   - 如果是"基准值"（比如 attack=100 代表基准），旧曲线用 ≤100→1.0 掩盖了它；新曲线需要显式设为基准值。
4. 估算新曲线下的实际数值：用 Python 脚本跑新旧对比
5. 把需要调整的数据项写进 prompt 的【改什么】段

完成标准：每个受公式影响的数据源，要么已更新数值，要么被你判断为"恰好正确"且有依据。**零遗漏。**
```

> **教训（2026-06-24 本 session）：** 修改攻击强度曲线后，所有怪物 attack=1 的伤害从正常变为接近 0，因为旧曲线把 attack=1 看作"基准值"(×1.0)，新曲线给的是 ×0.1。如果当时做了一个反向计算——"新曲线下 attack=1 是多少倍率？旧曲线呢？差多少？"——就能在推送前发现怪物攻击值需要上调。公式修改后永远要反问：旧公式下哪些"隐藏的假设"被新公式打破了？

### 文件拆分/重命名的向后兼容策略

当一个任务涉及**将一个大文件拆分为多个分类文件**（如 `item_templates.py` → `money_templates.py` + `equipment_templates.py` + ...），且原始文件被多处消费时，需要决定如何管理 imports。

#### 策略 A：保留原文件为纯 re-export hub（推荐当消费者多时）

原文件删除所有具体定义，改为从新文件 import 并 merge 后重新导出同名变量。优点：**消费方代码零改动。**

```python
# item_templates.py — 注册表合并中心
from world.money_templates import ITEM_TEMPLATES as _MONEY
from world.equipment_templates import ITEM_TEMPLATES as _EQUIP
from world.skill_book_templates import ITEM_TEMPLATES as _SKILL
from world.material_templates import ITEM_TEMPLATES as _MATERIAL
from world.talisman_templates import ITEM_TEMPLATES as _TALISMAN

ITEM_TEMPLATES = {}
for _d in (_MONEY, _EQUIP, _SKILL, _MATERIAL, _TALISMAN):
    ITEM_TEMPLATES.update(_d)
```

**适用条件：**
- 原文件被 3+ 个消费者引用，逐个改 import 工作量大
- 消费者是通用查找代码（loot 系统、描述同步），不关心具体类型
- 新文件各自是自包含的独立模板模块（延续 herb_templates/ore_templates 模式）

#### 策略 B：更新所有消费者 import（推荐当消费者少时）

直接删除原文件，逐一更新每个消费者的 import 路径。

**适用条件：**
- 消费者 ≤2 个
- 每个消费者只需要特定类型的 item（不需求合并在一个 dict 里）
- 或者愿意在消费者处自己 merge

#### 判断流程

```text
开始 → 原文件被多少文件引用？
  ├── ≥3 个消费者 → 策略 A（re-export hub）
  └── ≤2 个消费者 → 检查消费者是否只需要特定类型？
       ├── 是 → 策略 B（改 import）
       └── 否 → 策略 A
```

> **历史教训（2026-07-23 item_templates.py 拆分）：** Emma 最初想直接改消费方 import，但分析发现 game_util.py 有 8 处 `ITEM_TEMPLATES` 引用（含通用 loot 查找、任务奖励、货币查询），`at_server_startstop.py` 需要遍历所有物品同步描述——3 个消费者各自需要不同的子集。最终用策略 A（re-export hub）实现零消费者改动，拆分一次性通过 review。

### 复杂任务的 Prompt 增强

跨 3+ 文件的复杂任务，在写 prompt 前先做**代码库侦察**：

1. 搜索相关关键词找到所有涉及的文件
2. 读关键部分：类型定义、数据格式、已有类似实现
3. 确认**不改什么**边界

侦察产出在 prompt 中体现为：

- **参考文件**段 — 精确文件路径 + 文件职责一句话说明，帮助小弟快速定位上下文
- **约束**段 — 引用现有代码的约定（格式、命名、import 顺序），让小弟照做
- **不改什么**段 — 防误伤

> 读代码是为了让 prompt 更精准，不是为了替小弟做分析。产出的 prompt 仍然只引事实（"这个文件有 X 结构"），不引判断（"这里应该用 Y 模式"）。

~/.opencode/bin/opencode run '你的 prompt' \
  --model opencode-go/deepseek-v4-pro \

# Flash 任务（简单修改）

  --model opencode-go/deepseek-v4-flash \

### ⚠️ 不设 timeout，用 background 模式

**所有 OpenCode 调用必须用 `background=true + notify_on_complete=true`，不设 timeout。** 原因：

- OpenCode 执行时间不可预测（模型思考、文件读写、工具调用链等）
- 设 timeout 会导致输出被截断，小弟活干了一半被 kill，留下一堆未 commit 的改动
- background 模式让进程跑完再通知你，不会阻塞当前对话

```python
terminal(
    command="cd <项目路径> && ~/.opencode/bin/opencode run '你的 prompt' --model opencode-go/deepseek-v4-xxx --format json",
    background=True,
    notify_on_complete=True,
)
```

### 超时（进程真的挂了）的处理

OpenCode 在 background 模式下跑完会自动通知你。如果长时间没收到通知，先查日志：

```bash
tail -50 ~/.local/share/opencode/log/opencode.log
```

确认是"慢"还是"死了"：

| 现象 | 日志特征 | 判断 | 措施 |
|:----|:---------|:-----|:-----|
| 正常的慢 | 日志持续有 loop step 增长 | 还在跑 | 继续等，别动 |
| 真挂了 | 日志最后有 ERROR/异常，或长时间无更新 | 进程死了 | 查 git diff --stat 看有没有改到一半的文件，再决定是否重跑 |
| 静默僵死 | 日志停在某步，没 ERROR 也没推进 | 树莓派上偶发的 OpenCode 子进程僵死 | 杀进程（`process action=kill`），然后手动收尾 |

### 多阶段任务

如果任务需要分多阶段完成（比如先分析再实现），**每个阶段都是一个独立的 OpenCode 调用**，每次调用都遵循本 skill 的完整流程（消歧→判断类型/选模型→写 prompt→执行）：

```
回合 1: OpenCode run "分析 X 模块的结构，输出..."
        → 得到分析结果
回合 2: OpenCode run "基于分析结果，实现 Y 功能..."
        → 每个回合都是独立的 high-signal prompt
```

每个回合的 prompt 中，上一回合的输出可以作为"背景事实"引用（不是"Emma 的分析"），但不要加上 Emma 自己的判断。

### 功能拆解与分步实施（增量开发）

当用户描述了一个包含**多个子模块的新功能**时（如采药系统包含：药材模板 + 稀有度池 + tick 逻辑 + 命令 + 房间标记），不要默认全部路由给小弟一次做完。

用户可能希望逐步推进、每步审核。**先问清楚节奏。**

#### 标准流程

```
功能拆解为 N 个子模块
    ↓
子模块 1: Emma 出设计/内容 → 用户审核 → 路由小弟实现 → 验证交付
    ↓ (收到 "继续"、"下一步" 等确认信号后)
子模块 2: 同上
    ↓
...
```

#### 内容/交互设计阶段（Emma 做）

对于**内容类设计**（命名、文案、数值平衡）和**交互功能设计**（命令交互流程、面板UI、多步操作流程），Emma 先出设计稿：

1. 理解用户设计意图
2. 输出完整的设计草案（名称、数值、规则说明、交互流程、边界情况）
3. *不包含实现方案*（具体代码交给小弟）
4. 等用户审核确认后再路由给小弟

> **内容设计的审核门槛：** 用户说"完美"、"拍板"、"没问题"或者直接说"让小弟开工"才算通过。用户只是"嗯"或"看看"说明还在审，别急着派活。
>
> **进阶技巧：多旋钮设计方案** — 当用户提出开放性问题（"你觉得可以怎么优化？" / "有什么方案？"），不要只给一个方案。把设计空间拆为多个独立维度（旋钮），每个旋钮给 2-3 个选项并说明利弊，让用户逐项选择：
> ```
> 旋钮 1：耗时公式 — A. 线性 / B. 指数
> 旋钮 2：中断处理 — A. 进度保留 / B. 进度清零
> 旋钮 3：门槛条件 — A. 无门槛 / B. 悟性<60 读不懂
> 旋钮 4：稀有度耗时 — A. 10/20/30/40/50/60 / B. 5/10/20/40/80/160
> 旋钮 5：暴击效果 — A. 有 / B. 无
> → 用户逐条回复 -> Emma 按每个选择编译完整设计稿 -> 再次确认 -> 路由小弟
> ```
> 用户反馈信号通常是逐条编号回复（"1. X；2. Y；3. Z"）。收到后按每项选择编译为完整设计稿，发一次确认再路由小弟。适用场景：非紧急的体验优化/数值平衡/系统扩展。紧急或边界清晰的任务不需要拆旋钮。

#### 逻辑实现阶段（小弟做）

内容设计审核通过后，走标准路由流程派小弟实现典型的规则：

- 每次只派一个子模块，不做批量预设
- 等待用户明确确认后再推进下一个
- 交付时附一手证据（git diff、语法检查等）

#### 用户节奏信号

| 信号 | 处理方式 |
|:----|:---------|
| 用户说"一步一步来"、"慢慢实现"、"先做 X" | **严格遵守分步实施**，绝不一键全抛 |
| 用户说"一把梭"、"全部做完"、"一起搞定" | 可以一次性派小弟 |
| 设计提交后用户沉默或只说"看看" | 等明确信号，不要主动推进下一步 |
| 用户说"让小弟开工吧"、"让小弟改代码" | 内容设计审核通过，可以路由给小弟了 |

### 多任务清单 — 用户说要做好几件事

当用户一次性列出 2+ 个独立任务时（如"先做 A，再做 B，然后 C"），**不要默认一次全做完**。先识别用户的执行节奏信号：

| 用户信号 | 处理方式 |
|:---------|:---------|
| 用户说"一个一个来" / "先做前两个" / "先做 A" | **严格遵守。** 做完一个 → 交付一手证据 → 等 review → 再做下一个。不要自作主张全做完。 |
| 用户说"挨个修复，每个修完提交一下代码，全部修完了我一起测试" | **逐个派单 + 单独提交 + 批量验证。** 每个任务独立 dispatch 给小弟，各单独 commit 但不逐个等 review。全部完成后再一次性做语法检查/功能验证/汇报。推送到远程的时机：要么全部完了一起推，要么用户说"一起测"后推。 |
| 用户没有明说节奏 | **先问清楚：**"这些任务我依次做完了汇报给你，还是一个一个来？" 不要猜。 |
| 用户说"全部做完" / "一起搞定" / 明确要求一次过 | 可以一次性派小弟全做。 |

逐个执行但批量验证的流程：

```
任务 1: 消歧 → 代码库侦察 → 写 prompt → 派小弟(background) → 提交(不推)
   ↓ (继续，不等 review)
任务 2: 同上 → 提交(不推)
   ↓
任务 N: 同上 → 提交(不推)
   ↓ (全部完成)
批量验证: 语法检查 + import 验证 + 功能断言
   → 汇报 + 附 commit hash 列表 + 问是否推远程/测试
```

> **⚡ 小改动批量优化：** 当 3+ 个独立小改动（每个 <30行、单文件、已审过scope、互不依赖），可以**合并在一个 prompt 里派给小弟**，要求它分别提交。避免 3 次独立的 background dispatch 开销。前提是 prompt 里明确写明每个改动独立的 commit 要求和 Conventional Commits 消息。此 session 的 #8 #9 #10 即采用此模式：一次 dispatch 出 3 个独立 commit，比三次派单省 2/3 开销。

逐个执行+逐个 review 的流程：

```
任务 1: 消歧 → 代码库侦察 → 写 prompt → 派小弟(background) 
         → 交付 + 一手证据(verify) → 等 review
    ↓ (收到 review/OK 信号后)
任务 2: 同上
    ↓
...
```

关键规则：
- **每个任务走一次完整的 code-task 流程**（消歧 → 判断 → 写 prompt → 执行），不做预先的全盘分析
- **不要一次写多个任务的 prompt 然后批量发**——这等于你在替用户做优先级编排，违背纯路由原则
- **等待 review 信号**——用户说"下一个"、确认 OK、或者主动推进，才算可以继续。用户没说话就是还在审
- 如果任务是互不依赖的，等所有任务都 review 完后，再根据反馈一次性修正
- **推送时机：** "逐条提交"场景下，只 git commit 不 git push，避免推到一半用户让改。等到全部完成 + 用户确认后再统一推送。

## 🔄 分析到行动（Analysis-to-Action）管道

当用户先要求"分析/评估"某个项目，然后基于分析结果决定修什么时，有一个清晰的管道流程：

```
Phase A: 派小弟做全量架构/技术债分析
    ↓ 得到分析报告（含分级清单、修复建议）
Phase B: Emma 汇总 → 呈现给用户（按 🔴🟡🟢 分级）
    ↓ 用户挑选要修的条目
Phase C: 用户问 "你有什么建议？" → Emma 给出推荐 + 选项
    ↓ 用户确认
Phase D: 按多任务工作流 dispatch 修复
    ↓
Phase E: 全部完成 → 批量验证 → 推送/测试
```

**关键规则：**
- **Phase A** 小弟的输出（修复建议、方案选项）直接作为 Phase C 中 Emma 向用户呈现的素材。Emma 不需要重新分析，但需要把小弟的结论组织成清晰的分级清单 + 可选的方案对比。
- **Phase C** 触发的例外规则：用户主动问"你有什么建议"时，Emma 可以把小弟的方案选项精简为 2-3 个，**加上自己的推荐**（code-task 允许的"用户征求设计意见"例外）。
- **Phase D** 遵循多任务节奏规则：用户说"都修了吧"→批处理；"一个一个来"→逐个派；"每个单独commit，全部完了一起测"→逐条提交+批量验证。小改动可合并一次 dispatch（见上面批量优化说明）。

## 坑

### ⚠️ 小弟的 file read 工具被限定在项目目录内

OpenCode 小弟的 `read`/`search_files` 等文件工具被限定在**启动项目目录内**（因为 OpenCode 的安全机制）。headless 模式（`--format json`）下跨目录读文件会触发 `auto-rejecting` 且不会提示你，导致小弟拿不到源码但继续用推测干活。

**常见场景：** 需要读 Evennia、Django 等框架源码来理解底层行为，但框架安装目录（如 `/home/qn/projects/evennia/`）在项目目录之外。

**解决方案（按优先级排序）：**

1. **在 prompt 中直接提供框架 API 信息** — 把关键 API 的签名、行为、源码片段写进 prompt 的【背景事实】段，让小弟不需要自己读。这是最稳的方式，因为不依赖文件系统。

2. **在项目内创建 symlink 指向框架源码目录** — 将框架源码通过 symlink 映射到项目目录内（如 `XunDaoMUD/_evennia_ref → /home/qn/projects/evennia`），**必须添加 `.gitignore`** 防止提交：
   ```bash
   ln -s /home/qn/projects/evennia /home/qn/projects/XunDaoMUD/_evennia_ref
   echo "_evennia_ref" >> .gitignore
   ```
   小弟读 `_evennia_ref/evennia/scripts/tickerhandler.py` 就在项目目录内，不触发权限门。

3. **从项目根目录外启动 opencode** — 理论上可行但会丢失项目级 AGENTS.md 和上下文，不推荐。

> **历史教训（2026-06-21）：** Emma 三次派小弟分析 Evennia TickerHandler 的 remove 行为，三次被跨目录权限挡住。最终方案是 prompt 里写全 TickerHandler API + symlink 兜底。

### ⚠️ Prompt 里塞代码片段 = 替小弟做实现

**不要把实现代码写进 prompt。** Prompt 只描述"要什么行为"和"参考哪个现有模式"，不贴 Python 代码。

错误示例：
```
# ❌ 别这么干
在 stop 命令里加：
elif caller.ndb.idle_task == "caiyao":
    _stop_caiyao(caller)
    caller.msg("你停止了采药。")
```

正确示例：
```
# ✅ 这么写就够了
在 stop 命令中追加 elif 分支处理 idle_task == "caiyao" 的停止，
参考 cultivate 和 liaoshang 的分支写法。
```

例外：纯数据定义（config 值、枚举列表、item 模板的 dict 结构）可以展示字段格式，但仅限于数据结构约定，不含逻辑代码。

> **历史教训（2026-07-11）：** Emma 在采药系统的 prompt 中直接写了 stop.py 的 elif 代码片段和 PlayerCharacter 的回调实现。用户指出"不要直接把代码传给小弟，你负责准确转述开发需求"。

### ⚠️ Evennia 命令中不要等待裸 "yes" 输入做确认

当在 Evennia 命令中需要多步确认时，**不要设置 `caller.ndb._expecting_xxx` 状态后等待玩家输入 "yes"**——Evennia 的命令解析器不会把裸 `yes` 路由到你的命令，会报"「yes」不是可用命令"。

正确做法：让玩家**重复输入完整命令**来完成确认。比如 `skills forget X` 需要玩家连续输入三次完整命令（第一次开始，第二次确认，第三次最终执行）。在 `func()` 开头检查 pending 状态，如果当前输入匹配 pending 操作的子命令+参数，推进 step；否则取消 pending。

**详见：** `skill_view(name="code-task", file_path="references/evennia-command-interaction-patterns.md")` 的「模式 1：双重确认」章节。

> **教训（2026-06-23 本 session）：** Emma 让小弟实现了 skills forget 采用等待 "yes" 输入的方式。玩家输入 "yes" 后提示「yes 不是可用命令」。修复方案改为重复输入完整命令的确认流。

**不要因为改动看起来小就跳过 OpenCode 直接 patch。** 这是 code-task 被违反最常见的原因——Emma 觉得"只是改几个常量值/加几行命令/换个字符串，不值得走一轮 OpenCode"。

只要改动**改变玩家体验或系统行为**，不论改量大小都必须走 OpenCode：

- CSS 影响渲染 → 走 OpenCode
- JS 影响行为 → 走 OpenCode
- 命令/后端逻辑改动 → 走 OpenCode
- Config 改变逻辑行为 → 走 OpenCode

**唯一例外：纯数据变更**（改 YAML/JSON/TOML 的静态常量值、加一条 NPC 对话记录、更新静态数据表，且不改变程序逻辑）才允许 `write_file` 直写。

**常见触发场景：**
1. 用户描述需求后没直接说"派小弟"，Emma 自己用 patch 改了 → ❌ 必须先消歧再路由，不替用户做跳过决策
2. 改动经设计审核后，Emma 觉得"反正都过审了，直接改更快" → ❌ 流程没有"审核过了就能跳过"的例外
3. 修 bug 时定位到根因，自己用 patch 修了 → ❌ 即使是单行修复也必须走 OpenCode

**判断标准：** "如果这个改动被发现有 bug，用户会觉得是我的问题还是小弟的问题？"答案是 Emma 的问题——因为代码是 Emma 写的，没有经过工具链验证。

> **教训（2026-06-23 本 session）：** 用户让加心法替换功能，Emma 用 `patch` 直接改了 `skill_menu.py` 和 `idle_tasks.py`（121 行），被用户当场抓包"为什么不加载 code-task？"——技能里写得很清楚"无例外"，但自己找理由绕过了。正确做法：加载 code-task → 写 prompt → 派小弟，无论改量大小。

### ⚠️ 前端定时刷新型 UI：小弟默认重建 DOM，CSS 过渡不生效

当任务涉及**周期性刷新前端界面**（战斗 tick 刷新面板、定时器面板、轮询状态卡片等），小弟的默认做法是每次收到数据就清空容器（`parent.empty()`）然后重新创建所有 DOM 元素。这导致 CSS `transition` 永远不触发——因为元素在每次更新时都是全新的，不是同一个 DOM 节点。

**错误表现：** 资源条本该平滑增减，实际是跳变。因为小弟写的是：
```js
battlePanel.empty();
// 重新创建所有卡片
```
而不是：
```js
// 更新已有元素的宽度（CSS transition 生效）
card.find('.hp-fill').css('width', newPct + '%');
```

**解决方案：** 在 prompt 中埋入一条约束——
> **增量 DOM 更新：** 所有周期性刷新的 UI 组件，必须使用增量更新模式。首次渲染创建 DOM 结构，后续更新只修改已有元素的属性（`width`、`text`、`class` 等），禁止清空后重建。

如果是后端数据驱动的刷新（战斗 tick、状态轮询等），一定在【约束】段加上这条。

> **历史教训（2026-06-21 战斗面板）：** 小弟初始实现每次 combat tick 都 `battlePanel.empty()` 重建卡片，体魄/灵力/神识条只能跳变无法动画。Emma 手动改为增量更新后，`transition: width 0.3s ease` 才生效。用户评价「从功能角度来说不错，但是能不能把三种资源条的减少/增加做成渐变式填充」。

### ⚠️ 代码行为查询 ≠ 代码分析/实现：先读代码再回答，不猜不编

**核心原则：当用户问"这段代码怎么工作的"、"如果 X 会发生什么"、"模拟一下 Y 场景"，这是 Emma 直接读代码回答的职责，不要路由给小弟。**

当用户问代码行为相关的问题时，你必须：

1. **先识别任务类型：**

### ⚠️ 后端广播时序问题伪装成 CSS 动画不生效

当用户反馈实时 UI 元素（如进度条、填充条）「不动」「一直黑的」「没动画」时，**不要默认从 CSS/JS 找原因**。先检查服务端广播时机：

```python
# ❌ 错误的广播时序：前端永远看不到峰值
tick():
    AP 累加        # 50→150
    _resolve_actions  # 扣100→50
    广播             # 前端只看到 50% → "一直黑的"

# ✅ 正确的广播时序：前端先看到峰值
tick():
    AP 累加        # 50→150
    广播             # 前端看到 100% → 开始动画填充
    _resolve_actions  # 扣100→50（下次广播才回缩）
```

诊断方法：
1. **查看服务端广播时的数据值**（在 `_broadcast_battle_status` 调用前打印 ap 值）
2. **查看广播和状态变更的执行顺序**（广播在前还是状态变更在前？）
3. **在浏览器 DevTools Network/Console 中查看收到的消息数据**，看数值是否真的在变化
4. 如果在一次 tick 内广播了两次（变化前+变化后），前端只会看到最终值。CSS 动画永远不触发

> **经验（2026-06-22 AP 填充条）：** 用户反馈 AP 填充条「一直黑的没动画」，初看以为是 CSS 颜色太暗，实际根因是 `_broadcast_battle_status` 在 `_resolve_actions` 之后执行，前端永远只能看到扣除后的小数值。把广播挪到 resolve 之前即解决。

### ⚠️ NPC show_if 不防关键词直访 + complete_quest 不防重复

交付分支的两个叠加安全漏洞：
1. `show_if` **只在 `ask <npc>`（无关键词）列出选项时检查**。玩家直接 `ask npc 关键词` 会绕过守卫。
2. `complete_quest` action **不检查 `quest_states[quest_key] == "completed"`**，每次重新发奖励。

**修复方案详见 `references/evennia-npc-quest-and-inventory-pitfalls.md`。**

### ⚠️ `random.choices` 动态权重求和为零

当词条/概率池的权重从数据字段动态提取时（如 `affix_weights = [a.get("rarity", 50) for a in pool]`），如果某条数据的 `rarity` 字段值为 0，权重就是 0。若池子中所有可用数据的权重都为零，`random.choices()` 会抛 `ValueError: Total of weights must be greater than zero`。

**解决方案：** 提取权重时加 `max(w, 1)` 兜底：

```python
# ❌ 危险：如果有数据 rarity=0，random.choices 会炸
weights = [a.get("rarity", 50) for a in pool]

# ✅ 安全：最小权重为 1
weights = [max(a.get("rarity", 50), 1) for a in pool]
```

> 教训（2026-07-22 推演词条抽取）：玩家投入 0 资源后 `_draw_affix_candidates` 报错，因为 tier_available 中某个词条的 rarity=0 导致权重列表全零。一行 `max(..., 1)` 修复。

> **历史教训（2026-07-23）：** 铁匠上线后同时发现两个 bug：矿石不移除 + 任务可重复刷精铁剑。使用 NPC 对话系统时交付分支**必须在三个层面做防护**：`show_if` 守卫、`conditions` 验证、`complete_quest` 防重检查。
